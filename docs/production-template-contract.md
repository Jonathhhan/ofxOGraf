# Production Template Contract

This contract defines the minimum boundary for a template that is allowed to move from
authoring into a production package. It applies equally to the native openFrameworks preview,
the WebAssembly build, and the OGraf web component.

The contract is deliberately small. A template can contain more data, but it must not weaken
these guarantees.

## 1. Identity and version

Every template has a stable identity and an explicit authored scene version:

```json
{
  "id": "com.example.ltr-rtl",
  "format": "broadcast-scene",
  "version": "0.3.0",
  "generator": "ofxOGraf",
  "provenance": [{
    "tool": "ofxOGraf",
    "version": "1.0.0",
    "source": "example-tutorials"
  }]
}
```

The `id` is immutable once a template has been delivered. A visual redesign is a new version of
the same template; a change in control meaning or output contract requires a new template id.
Scene migration is owned by the loader and follows `docs/scene-compatibility.md`.

## 2. Render contract

The template must declare the output it was authored and tested for:

```json
{
  "renderRequirements": [{
    "width": 1920,
    "height": 1080,
    "frameRate": 50,
    "pixelAspectRatio": 1,
    "alpha": true,
    "colorSpace": "sRGB",
    "accessToPublicInternet": {"exact": false}
  }]
}
```

Native and WebAssembly must use the same logical coordinate system, frame rate, time units, and
alpha convention. The Scene Renderer may use a different physical surface size, but the resulting scene
coordinates and timing must remain equivalent.

## 3. Controls

Controls are the public API of a template. They require stable ids, types, defaults, and bounds.
Controls must never be addressed by display labels or layer indices.

```json
{
  "controls": [
    {
      "id": "headline",
      "name": "Headline",
      "type": "string",
      "default": "Hello world",
      "maxLength": 80
    }
  ]
}
```

Every control update must be safe when omitted, repeated, reordered, or received before the first
render. Invalid values are rejected or clamped deterministically and produce a diagnostic.

## 4. Assets and fonts

Every referenced asset is packaged locally and has one canonical path. Network URLs are forbidden
in production packages. Fonts are part of the template contract, not an installation prerequisite.

For text, the production contract additionally requires:

- explicit `direction`, `script`, and `language` for every shaped run;
- HarfBuzz shaping for editable Unicode text;
- deterministic fallback or a declared unsupported range;
- a test fixture for every script used by the template;
- no mixed-script content hidden inside a run whose shaping metadata describes another script.

The LTR/RTL tutorial is the reference fixture: Arabic and Latin labels are separate runs, while
the scene still demonstrates both directions in one composition.

## 5. Feature policy

Each feature used by a production template must be in one of these states:

| State | Meaning |
|---|---|
| guaranteed | Native and WebAssembly render it equivalently and tests cover it |
| extension | A declared runtime extension handles it |
| baked | It is delivered as a deterministic image/sequence fallback |
| preview-only | It may be shown during authoring but cannot ship on-air |

Undeclared fallback is not allowed. Unsupported layers must be reported before packaging.

## 6. Validation gates

A template is production-ready only when all gates pass:

1. schema validation and scene migration checks;
2. asset, font, license, and offline-package validation;
3. native load/render test;
4. WebAssembly load/render test;
5. HarfBuzz and control contract tests;
6. golden-frame comparison at the declared output settings;
7. reproducible package creation and package verification.

Compilation is evidence only for the build. It does not replace runtime or image validation.

## 7. Delivery layout

The delivered package contains only declared, reproducible inputs:

```text
template/
  manifest.json
  scene.json
  template-definition.json
  data/
    fonts/
    images/
  package-bom.json
  package-integrity.json
```

`manifest.json` identifies the template, runtime compatibility, render requirements, and package
version. `package-integrity.json` and `package-bom.json` are generated by the existing package
scripts; they are not hand-edited.

## 8. Reference implementation order

The first complete vertical slice is `text-ltr-rtl.scene.json`:

1. add stable identity and render requirements;
2. make the four text runs the canonical shaping fixture;
3. add native and WebAssembly golden frames;
4. validate and package it offline;
5. use the same checks for every later template.

Until this slice passes all gates, new Scene Renderer features should remain experimental rather than
being presented as production guarantees.
